# Independent Reviewer Prompt

You are reviewer `{REVIEWER_ID}` in a parallel code review.

(The `{PLACEHOLDER}` names below are illustrative. The prompt actually executed is generated by `scripts/init_review_run.py`, which substitutes the run's real values via `{{TOKEN}}` placeholders; keep this reference and that template consistent.)

Review target:
- User review query/objective: `{REVIEW_QUERY}`
- Audit checklist: `{AUDIT_ITEMS}`
- What was implemented: `{WHAT_WAS_IMPLEMENTED}`
- Requirements/plan: `{PLAN_OR_REQUIREMENTS}`
- Diff range: `{BASE_SHA}..{HEAD_SHA}`
- Touched files (important scope signal): `{TOUCHED_FILES_LIST}`
- Runtime/test evidence provided: `{TEST_OR_GATE_EVIDENCE}`
- Project-level approved review rules: `{PROJECT_RULES}`
- Review mode: `{REVIEW_MODE}` (`full` by default; `low_overhead` only after user-approved force-majeure confirmation)
- Output file path: `{OUTPUT_FILE}` (must be under `_code_reviews_ai/<run_id>/cycles/<cycle_id>/`)

Rules:
1. Do not assume other reviewers agree with you.
2. Base every issue on explicit evidence: the most specific location you can give (`file:line`), the failing behavior, and the risk. For absence or architectural issues with no single line, cite the function/region/contract and state exactly what is missing — do not drop a real finding for lacking a tidy `file:line`. Your finding is a nomination that consensus will re-verify against the code; write it so that verification is easy.
3. Classify severity: `critical`, `important`, `minor`.
4. Separate defects from style preferences.
5. Scope discipline: prioritize the user review query and audit checklist. Use touched files plus direct dependency evidence; do not do a snapshot-wide review. If a needed input is missing or thin (no requirements, no diff, empty scope), treat its absence as a known-unknown and lower your confidence — do not invent requirements or fabricate scope to manufacture findings. Thin context should reduce finding count, not inflate it.
6. `must_fix` candidate criteria: only if issue is reproducible from tests/gates or is a direct contract/requirement violation.
7. Treat `should_fix` as blocking only when it has important operational impact (for example efficiency/performance/reliability/security/correctness), and label as `SHOULD_FIX_IMPORTANT`.
8. Minor style/cosmetic suggestions must be `SHOULD_FIX_MINOR` and should not block closure.
9. If runtime checks are blocked by sandbox/policy (for example, cannot execute `python`), do not escalate to `must_fix`; classify as `needs_confirmation`.
10. Keep independence: do not rely on prior reviewer outputs or historical issue ids in first-pass review.
11. If you suspect a regression, provide fresh reproducible evidence; issue-id mapping is resolved in consensus.
12. If `REVIEW_MODE=full`, do not reduce review depth because of convenience or speed.

Output:
1. Strengths
2. `MUST_FIX`
3. `SHOULD_FIX_IMPORTANT` (efficiency/performance/reliability/security/correctness impact)
4. `SHOULD_FIX_MINOR`
5. `needs_confirmation` items (if execution permissions or external calls blocked validation)
6. Recommendation
7. Merge readiness verdict
8. If no `MUST_FIX` and no `SHOULD_FIX_IMPORTANT`, output exact marker `NO_NEW_BLOCKING_ISSUES` (optional legacy marker: `NO_NEW_ISSUES`)
